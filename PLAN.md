# Campus Incident Reporting App — Build Plan

> North star: a student reports a campus problem in under 30 seconds and watches it get fixed in real time; staff triage it from one screen. Everything in this plan serves that sentence or the 55-point rubric. If a task serves neither, it is cut.

---

## 0. Ground rules (guardrails)

**How we work**
- One phase at a time. Each phase ends with a **checkpoint**: I show screenshots / a run, list what's done vs. the exit criteria, and you approve or request changes. No next phase without your "go".
- Each phase iterates internally (build → run → screenshot → fix) until its exit criteria pass. I don't hand you a half-done phase.
- Git: one branch per phase (`phase/1-design-system` …), small commits, merge to `main` after approval. Tag each approved phase (`v0.1`, `v0.2`, …) — easy rollback.
- `flutter analyze` = 0 issues and `dart format` clean before every checkpoint.

**Scope IN (rubric-required)**
Auth (register/login/logout/reset/verify/session/domain check), student + staff roles, report with category/title/description/location/optional photo, live feed with search + filters, details with status timeline, staff status/priority/resolution controls, security rules, loading/empty/error states, tests, IEEE report, demo video.

**Scope IN (cheap, high rubric value — "Product thinking")**
Anonymous-reporting toggle, open-report rate limit, staff "hide as spam", in-app notifications list, edit/delete own report while still *Submitted*.

**Scope OUT (do not build)**
Push notifications (FCM), chat/comments, maps/GPS, dark mode, localization, admin web panel, analytics charts, multiple photos, Cloud Functions, offline-first sync beyond Firestore's default cache, onboarding carousel.
_(Any of these only if you explicitly ask.)_

**Underbuild traps to avoid** — things easy to forget that cost points:
email verification gate, staff-mode details screen, Firestore indexes, Storage rules, history timeline data, empty states, upload progress, form validation messages, demoing the Firebase Console.

## 2. Design system (built once, used everywhere)

From the mockups:

- **Colors**: primary `#8B2BE2`-ish purple (exact value sampled from 1.png in Phase 1), primary-soft lavender for tiles, background `#F7F6FB`, surface white, text `#1A1A2E` / secondary `#6B6B80`.
- **Status colors** (pill bg / text): Submitted = amber, In Review = blue, In Progress = purple, Resolved = green. One `IncidentStatus` enum owns label + colors + icon.
- **Categories**: Facilities, Water, Electricity, Safety, Sanitation, **Furniture** (6th added to match spec). One `IncidentCategory` enum owns label + icon + tint.
- **Tokens**: spacing 4/8/12/16/24/32; radius 12 (inputs) / 16 (cards) / 24 (hero); one soft shadow; type scale = display 26, title 18, body 15, caption 12.
- **Motion**: only 3 kinds — page transitions (default), pill/status change cross-fade, press-scale on tappable cards. Respect reduced motion.
- **Accessibility**: 48dp touch targets, contrast ≥ 4.5:1 on text, semantic labels on icon buttons, text scales to 1.3× without overflow.

**Reusable widgets (`lib/ui/widgets/`)**
`AppScaffold`, `AppBottomNav` (raised center +), `PrimaryButton` (loading state), `AppTextField`, `CategoryTile`, `StatusPill`, `StatTile`, `IncidentCard`, `StatusTimeline`, `FilterChipsBar`, `SearchField`, `PhotoPickerBox`, `HeroBanner`, `EmptyState`, `ErrorState`, `SkeletonCard`, `ConfirmDialog`, `Avatar` (initials fallback).

## 4. Data model

```
users/{uid}
  name, email, role: "student"|"staff", department, photoUrl?, createdAt

incidents/{id}
  title, description, category, location, photoUrl?, photoPath?,
  status: submitted|inReview|inProgress|resolved,
  priority: low|medium|high, isAnonymous, isHidden,
  reporterId, reporterName, resolutionNote?, createdAt, updatedAt

incidents/{id}/history/{hid}
  from, to, byUid, byName, note?, at            # drives StatusTimeline

users/{uid}/notifications/{nid}
  incidentId, title, message, read, at          # written by staff action in a batch
```

**Indexes:** (status, createdAt desc), (category, createdAt desc), (status, category, createdAt desc), (reporterId, createdAt desc), (isHidden, createdAt desc).
**Search:** server filters by status/category; title/location substring match on client. `shortcut: client-side search, fine < ~1k docs, upgrade to Typesense/Algolia beyond.`
**Locations:** fixed list in `constants` (Blocks, Residence, Cafeteria, Library…) + "Other (type it)".

## 5. Security model

**Firestore rules**
- `users`: read self (staff may read all); create self only with `role == "student"`; update self but never `role`.
- `incidents` read: signed-in + verified; non-staff can't see `isHidden == true` unless owner.
- create: `reporterId == auth.uid`, `status == "submitted"`, field whitelist, title 3–80 chars, description 10–1000.
- update by owner: only while `submitted`, only title/description/category/location/photo.
- update by staff: only status/priority/isHidden/resolutionNote/updatedAt.
- delete: owner while `submitted`.
- `history`: create by staff only; read by all signed-in.
- `notifications`: owner read/update `read`; staff create.
- `isStaff()` = `get(/users/$(uid)).data.role == "staff"`; `isVerified()` = `request.auth.token.email_verified`.

**Storage rules:** write to `incidents/{uid}/{file}` only by that uid, `image/*`, < 5 MB; read by signed-in.

**Staff promotion:** manually in Firebase Console (documented in README + report). Domain allow-list: `alustudent.com`, `alueducation.com` (to confirm).

**Anti-abuse:** verified campus email only; max 5 open reports per student (checked in controller + documented as limitation since rules can't count); staff hide-as-spam.

Rules are tested with the Firebase emulator (Phase 6).

## 6. Phases

Each phase: **Goal → Tasks → Exit criteria → Checkpoint (what you review)**.

### Phase 0 — Foundation & setup (small)
- Tasks: `flutter create` (android + ios only, org `com.alu.campusincident`), folder skeleton, lints, git init + `.gitignore`, Android emulator ready, Firebase project + `flutterfire configure` (needs your login), enable Email/Password auth, Firestore, Storage (**Blaze plan check**).
- Exit: blank app runs on Android emulator connected to Firebase; `flutter analyze` clean.
- Checkpoint: you confirm Firebase project + email domains.
- **Needs you:** `firebase login`, Blaze decision, emulator or phone.

### Phase 1 — Design system & widget library
- Tasks: theme tokens, enums with colors/icons, all reusable widgets, a hidden `/gallery` debug screen showing every widget in every state (loading, disabled, error, each status pill/category).
- Exit: gallery screenshot matches mockup style; text scale 1.3× no overflow.
- Checkpoint: you approve the look (colors, font, spacing) **before** any screen is built — cheapest place to change taste.

### Phase 2 — Static screens (pixel pass, fake data)
- Tasks: all 12 screens built with an in-memory fake repository behind the same Riverpod providers (so Phase 3+ only swaps the repository). Navigation and shells wired, staff and student modes toggleable in debug.
- Screens: Splash, Login, Register, Verify Email, Forgot Password, Home, Report form, Feed (search + chips), Details (student + staff mode), My Reports/Profile, Notifications, Staff Dashboard.
- Includes empty, loading (skeleton) and error variants of every list.
- Exit: side-by-side screenshots vs. 1.png/2.png/3.png; every flow clickable end to end.
- Checkpoint: full UI review. **Iterate here until you're happy** — this is the "beautiful" phase.

### Phase 3 — Authentication (real)
- Tasks: AuthRepository, domain validator, register → write `users` doc → send verification → verify gate → login → session persistence → logout → forgot password; router redirects by auth + role; friendly Firebase error mapping.
- Exit: all auth flows on emulator; restart app keeps session; wrong domain rejected; unverified user blocked; staff account lands on staff shell.
- Checkpoint: demo run + Firebase Console Auth tab.

### Phase 4 — Reporting & data (real CRUD)
- Tasks: IncidentRepository + StorageRepository; report form controller with validation, compression, upload progress, success sheet; live streams for home stats, feed, my reports; edit/delete while submitted; anonymous toggle; rate limit; indexes deployed.
- Exit: create with/without photo, see it appear live on another device/emulator; edit/delete work; filters + search work on real data.
- Checkpoint: demo run + Firestore/Storage Console.

### Phase 5 — Staff workflow & live tracking
- Tasks: staff dashboard queue, status stepper, priority, resolution note, hide-as-spam; batch write (incident + history + notification); timeline from history; notifications screen with unread badge.
- Exit: staff changes status → student's details/timeline/notification update live within ~1s.
- Checkpoint: two-device demo.

### Phase 6 — Security hardening
- Tasks: write `firestore.rules` + `storage.rules`, emulator rules tests (student can't change status, can't set role staff, can't read hidden, can't upload >5 MB), deploy.
- Exit: all rule tests pass; app still works fully with rules deployed.
- Checkpoint: test output + short rules walkthrough.

### Phase 7 — Polish, edge cases & tests
- Tasks: offline/no-network messages, double-submit prevention, long text/huge counts/empty data (break-UI pass), keyboard handling, pull-to-refresh where useful, haptics on submit, a11y labels; unit tests (validators, models, time-ago, filter logic), widget tests (report form validation, status pill, login errors), repository tests with fakes; README.
- Exit: `flutter test` green; analyze clean; layer grep clean; release APK builds.
- Checkpoint: final app review + APK.

### Phase 8 — Deliverables
- Tasks: architecture + ER + sequence diagrams, annotated screenshots, IEEE-format report (architecture, schema, state mgmt, RBAC, UI/UX rationale, testing, challenges, limitations, references) as PDF; demo video script (7–10 min) mapped to rubric order; seed demo data; public GitHub repo.
- Exit: PDF with repo + video links; script you can record from.
- Checkpoint: you record the video.
